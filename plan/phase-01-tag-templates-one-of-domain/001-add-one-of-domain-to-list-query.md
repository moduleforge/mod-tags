# Add One Of Domain To List Query

## Purpose and scope

Add the `tag_purpose_policies.one_of_domain` flag to the `ListTagTemplates` sqlc query so the tag-templates catalog read carries each row's per-purpose exclusivity policy, and regenerate `model/db/`.

Files touched: `model/queries/tag_templates.sql` (hand-edited) and `model/db/tag_templates.sql.go` (regenerated — never hand-edited). No migration, no new query, no other file.

Covered by the standard implement-task procedure; no special skill.

## Requirements

1. **Rewrite the `ListTagTemplates` query** in `model/queries/tag_templates.sql` to add a left join against `tag_purpose_policies` and select a coalesced flag. The result must be:

   ```sql
   -- name: ListTagTemplates :many
   SELECT tt.purpose, tt.value, tt.label, tt.color, tt.sort_order,
          tt.scope, e.uuid AS scope_uuid,
          COALESCE(tpp.one_of_domain, false) AS one_of_domain
   FROM tag_templates tt
   LEFT JOIN entities e ON e.id = tt.scope
   LEFT JOIN tag_purpose_policies tpp ON tpp.purpose = tt.purpose
   WHERE tt.purpose = @purpose
     AND (tt.scope IS NULL OR tt.scope = sqlc.narg('scope')::bigint)
   ORDER BY tt.scope NULLS FIRST, tt.sort_order ASC, tt.value ASC;
   ```

   This is verbatim the pattern `model/queries/tags.sql` already uses on its `:many` queries (`ListTagsBySubjectEntityID`, `SearchTags`). Do **not** use the correlated-subquery-with-`::boolean`-cast spelling; that form exists in `tags.sql` only for `RETURNING` clauses, which cannot carry a join.

   `tag_purpose_policies.purpose` is the table's primary key, so this join can never fan out rows. The existing `ORDER BY`, `WHERE`, parameter names, and generated parameter struct must be unchanged.

   **This exact SQL was compile-verified during planning** against the composed schema with sqlc v1.31.1: `sqlc compile` passes and `sqlc generate` yields `OneOfDomain bool \`json:"one_of_domain"\`` as the trailing field of `ListTagTemplatesRow`, with `ListTagTemplatesParams` unchanged. If your run diverges from that, something else is wrong — halt and report rather than adapting the query.

2. **Leave `UpsertTagTemplate` untouched — including its leading comment block.** The 8-line `-- UpsertTagTemplate inserts or updates ...` comment above it is **not** decorative: sqlc propagates a query's leading comment into the `Querier` interface in `model/db/querier.go`. Dropping or reflowing it silently rewrites `querier.go` too. This was confirmed empirically during planning; treat the comment as part of the query.

3. **Regenerate `model/db/`** with sqlc. `ListTagTemplatesRow` must gain a trailing `OneOfDomain bool \`json:"one_of_domain"\`` field and the `rows.Scan` call must gain the matching `&i.OneOfDomain`. sqlc types the join-form `COALESCE(...)` as a plain Go `bool` — confirm it does, and if it instead emits `interface{}` or a nullable type, halt and report rather than working around it by hand.

4. **Do not hand-edit `model/db/`.** It carries a `// Code generated by sqlc. DO NOT EDIT.` header and `AGENTS.md` states generated code is committed but never hand-edited. If `sqlc` cannot be run, halt and report — do not synthesize the generated delta.

5. **Commit the regenerated file.** `model/db/` is committed to the repo per `AGENTS.md`.

### Toolchain preconditions

Run these from the task worktree root before anything else:

```sh
bash scripts/link-siblings.sh    # sibling-relative paths to mod-core; also run by `make preflight`
make -C model compose            # rebuilds the gitignored model/schema/migrations/ that sqlc reads

```

`model/schema/migrations/` is **gitignored** and absent in a fresh worktree; `sqlc generate` fails without composing it first. `make -C model build` runs `compose` then `sqlc generate` in one step and is the preferred invocation.

A **stale** composed directory is just as bad as a missing one, and its failure mode is confusing: a `schema/migrations/` left over from before `0205_tags_one_of_domain.sql` landed makes sqlc report

```
queries/tag_templates.sql:1:1: relation "tag_purpose_policies" does not exist
```

along with the same error for every pre-existing query in `tags.sql` — which looks like the new query broke unrelated code. It did not; the schema is stale. Re-run `make -C model compose` (which `rm -rf`s and rebuilds the directory) and retry before investigating anything else.

If `sqlc version` reports anything other than `v1.31.1` (the version in every generated file's `// versions:` banner), halt and report — regenerating with a different version rewrites the banner in every file under `model/db/`, producing a large diff unrelated to this change.
